# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Comandos

```bash
docker compose up -d   # Postgres local (porta 5432); --profile app roda também as migrações e a API
npm run db:migrate # aplica as migrações (DATABASE_MIGRATION_URL do .env, dono do schema)
npm run db:generate # gera a migração SQL a partir dos *.model.ts (drizzle-kit)
npm run dev        # tsx em modo watch, carrega o .env (precisa do Postgres com as migrações aplicadas)
npm run build      # tsc -p tsconfig.build.json -> dist/
npm start          # node dist/server.js
npm run lint       # eslint .
npm test           # vitest run (todos os testes)
npm run test:unit         # projeto "unit" do Vitest
npm run test:integration  # projeto "integration" (Postgres via Testcontainers, precisa do Docker)
npm run check      # lint + test + build — o que o CI roda nos PRs para master

npx vitest run tests/services/userService.spec.ts   # um único arquivo
npx vitest run -t "should throw when user already exists"   # um único teste pelo nome
```

Os testes carregam as variáveis de ambiente do `.env.test` via `tests/setup.ts` (`process.loadEnvFile`). O `.env.test` é versionado (só valores fictícios) e é o mesmo usado no CI: ao criar uma variável obrigatória nova, adicione-a nele também. O `src/config/secrets.ts` lança erro já no import se `JWT_SECRET`, `DATABASE_URL`, `RESEND_API_KEY`, `RESEND_EMAIL_ORIGIN`, `EMAIL_VERIFICATION_URL` ou `PASSWORD_RESET_HOST` estiverem ausentes, então qualquer teste que importe código da aplicação precisa desse arquivo. Os testes nunca acessam um banco real. São dois projetos no `vitest.config.ts`: **unit** (`tests/`, exceto `tests/integration/`), com repositórios e serviços mockados com `vi.mock` (o `src/db/db.js` é substituído pelo `tests/helpers/dbMock.ts`, cujas transações só executam o callback); e **integration** (`tests/integration/`), que usa `supertest` sobre o `app` e um Postgres 18 em container (Testcontainers) iniciado uma vez no `globalSetup`, que aplica as migrações num banco modelo. Cada arquivo cria um banco próprio a partir do modelo, esvaziado com `TRUNCATE` após cada teste (`tests/integration/setup.ts`). A API conecta com o mesmo papel de produção (`care_track_app`, sujeito a RLS e grants); para preparar dados e conferir o que foi gravado, use o `testDb()`/`adminQuery()` de `tests/integration/database.ts` (superusuário), e para provar o que o banco recusa à API, o `appClient()`. O Docker precisa estar rodando para os testes de integração, inclusive no `pre-commit`. Na integração, o único mock é o `email.service` (automock no setup); os tokens enviados por e-mail são lidos das chamadas do mock (`tests/integration/helpers.ts`). Como o Vitest define `NODE_ENV=test`, os rate limiters ficam ativos; o setup zera os contadores depois de cada teste. Toda rota nova deve ter teste de integração, incluindo o de isolamento entre enfermeiras.

Git hooks (husky): `pre-commit` roda lint + test + build; `commit-msg` roda o commitlint (Conventional Commits, regras em `docs/commits.md`). As mensagens de commit alimentam o semantic-release na `master` (`feat` → minor, `fix` → patch, `!`/`BREAKING CHANGE` → major), que em seguida faz o build e publica a imagem Docker em `ghcr.io/matheusalencar23/care-track-api`. O desenvolvimento acontece na `develop`; os PRs têm como alvo a `master`.

CI/CD (`.github/workflows/`): o `ci.yml` roda em PRs para `master`/`develop` e em push na `develop` — `npm run check`, commitlint sobre os commits do PR (e rejeição de mensagens vazias, que o commitlint ignora) e build da imagem Docker sem push. O `release-docker.yml` (push na `master`) chama o `ci.yml` e só então roda o semantic-release, que também grava a versão no `package.json` do workspace (`@semantic-release/npm` com `npmPublish: false`, sem commit) e publica a imagem no GHCR. Não há deploy: o fluxo termina no GHCR. A versão do Node fica no `.nvmrc` (e no `ARG NODE_VERSION` do Dockerfile, que deve acompanhar). Use o Node 24 (npm 11): o Dependabot gera o lockfile com o npm 11, e o `npm ci` do npm 10 (Node 22) recusa esse lockfile.

## Arquitetura

Express 5 + PostgreSQL 18 (Drizzle ORM sobre `pg`) + Zod, TypeScript ESM (`"type": "module"`, `NodeNext`). **Imports relativos precisam da extensão `.js`**, mesmo em arquivos `.ts`. O tsconfig é strict, com `noUncheckedIndexedAccess` e `exactOptionalPropertyTypes`.

- `src/server.ts` — bootstrap: conecta ao Postgres, sobe o servidor e faz o graceful shutdown. `src/app.ts` — pilha de middlewares (helmet, CORS com credentials, json, cookie-parser), monta `routes` em `/api/v1` e registra o `errorMiddleware` por último.
- `src/routes.ts` — monta `/users` e `/auth` com o rate limiter geral, além de `/health`. O `signin` usa também o `authLimiter` (mais restrito), aplicado na própria rota. Rotas que disparam e-mail usam também o `emailLimiter`, aplicado na própria rota. Os rate limiters são ignorados quando `NODE_ENV=development`.
- `src/modules/<feature>/` — camadas por feature: `*.routes.ts` → `*.controller.ts` → `*.service.ts` → `*.repository.ts` → `*.model.ts` (tabelas `pgTable` do Drizzle, com colunas em camelCase no código e snake_case no banco via `casing: "snake_case"`), com schemas Zod em `*.schema.ts`. Os IDs são UUID v7 gerados pelo banco (`uuidv7()`), e os params de rota são validados com `z.uuid()`. Controllers e services são exportados como funções nomeadas (sem classes) e importados como `import * as xService`, o que permite usar `vi.mock` pelo caminho do módulo nos testes.
- Validação: `schemaValidationMiddleware(schema)` valida `{ body, query, params }` de uma vez, então os schemas Zod têm o formato `z.object({ body: ..., query: ... })`. Falhas viram `UnprocessableEntityException` (422).
- Erros: lance subclasses de `HttpException` de `src/shared/exceptions/` (importe pelo barrel `index.js`); os controllers fazem `catch` e chamam `next(err)`. O `errorMiddleware` serializa `HttpException` via `toJson()` e transforma qualquer outro erro em 500. As mensagens para o usuário (em português) ficam em `src/shared/messages.ts`.
- Banco (`src/db/`): os repositórios sempre usam `getDb()` no momento da consulta. `withTransaction(fn)` e `withOwnerScope(ownerId, fn)` abrem uma transação e a guardam num `AsyncLocalStorage`, então tudo o que roda dentro do callback (repositórios e `auditLogService`) participa dela sem receber o executor por parâmetro; chamadas aninhadas reaproveitam a transação de fora. Use `single(rows)` para `INSERT/UPDATE ... RETURNING` de uma linha. Erro de chave única (`23505`) vira 409 no `errorMiddleware` (`isDuplicateKeyError`, de `src/utils/db.utils.ts`).
- Migrações (`migrations/`, na raiz e fora do build, copiada pelo Dockerfile): mude o `*.model.ts` e rode `npm run db:generate`; o que o drizzle-kit não gera (grants, triggers, funções) vai numa migração SQL própria (`npx drizzle-kit generate --custom --name=...`). Nunca edite uma migração já aplicada em algum ambiente. São aplicadas pelo `src/db/migrate.ts` (`node dist/db/migrate.js` na imagem; serviço `migrate` do compose) com a `DATABASE_MIGRATION_URL`, do dono do schema. A API usa a `DATABASE_URL`, do papel `care_track_app`, que não é dono das tabelas: tem só SELECT/INSERT e UPDATE nas colunas listadas em `migrations/0002_security.sql`, e nenhum DELETE. **Coluna nova que a API altera precisa de `GRANT UPDATE (coluna)` numa migração nova**, senão o update falha com `permission denied`.
- Autenticação: `POST /auth/signin` grava um JWT (1h, payload `{ sub }` com o id do usuário) em um cookie httpOnly `token` — não em header bearer. O `authenticationMiddleware` lê o cookie, verifica o token, carrega o usuário e define `req.user = { id, name, email, coren, corenState }` (tipado em `src/@types/express/index.d.ts`). O login exige que `emailVerifiedAt` esteja preenchido. Recursos que pertencem a um usuário devem ser sempre filtrados por `req.user.id` nas consultas.
- Isolamento por dono: tabelas de recursos que pertencem a um usuário (hoje `patients`, `consents`, `records` e `record_versions`) têm um `ownerId` — o profissional que controla o dado, nome genérico para não amarrar o modelo à enfermagem — e usam Row-Level Security: o `ownerIsolationPolicy(tabela)` (`src/db/columns.ts`) só deixa o `care_track_app` ver e gravar linhas em que `owner_id = app_current_owner_id()`. Essa função lê o dono definido pelo `withOwnerScope` (`set_config('app.owner_id', ..., true)`, que vale só até o fim da transação) e lança erro se ele não estiver definido, então toda consulta a essas tabelas precisa rodar dentro de `withOwnerScope(req.user.id, ...)` — fora dele, falha (vira 500) em vez de vazar dados. Os repositórios filtram por `ownerId` também, de forma explícita. Tabelas filhas apontam para o paciente por FK composta `(owner_id, patient_id) → patients(owner_id, id)`, o que impede ligar um registro ao paciente de outro dono, e um trigger (`reject_owner_change`) impede trocar o dono. Em toda tabela nova desse tipo (registros, arquivos): `ownerIsolationPolicy`, FK composta, trigger de dono imutável e grants, e prove o isolamento no teste de integração da rota (o `tests/integration/ownerScope.spec.ts` prova as garantias do banco com SQL direto).
- Fluxo de verificação de e-mail: no signup, o `emailVerificationToken.service` gera um token aleatório, guarda apenas o hash SHA-256 com expiração de 30 min, e o `src/services/email/email.service.ts` envia o token original via Resend como `${EMAIL_VERIFICATION_URL}?token=...`. `GET /users/validate` gera o hash do token recebido e checa a expiração e o `usedAt` (`findValidToken`), preenche `user.emailVerifiedAt` e marca o token como usado (`markTokenAsUsed`) na mesma transação, para que uma falha no meio não invalide o link. `POST /users/resend` sempre responde 200 (para não permitir enumeração de usuários). Os tokens de uso único usam `generateRandomToken`/`hashToken` de `src/utils/crypt.utils.ts`.
- Recuperação de senha: segue o mesmo modelo, com o `passwordResetToken.*` em `src/modules/auth/`. `POST /auth/forgot-password` sempre responde 200 e envia o e-mail sem bloquear a resposta; `POST /auth/reset-password` grava a senha e `user.passwordChangedAt`, invalida todos os tokens pendentes do usuário e audita, tudo numa transação. O `authenticationMiddleware` rejeita JWTs com `iat` anterior ao `passwordChangedAt`, o que derruba as sessões abertas antes da troca.
- Auditoria: `auditLogService.record({ userId, action, resourceType, resourceId?, patientId? })` (`src/modules/audit/`) grava quem fez o quê, em qual recurso e quando; o `requestId` e o IP vêm do contexto da requisição (`getRequestContext`). Aguarde a chamada — se a auditoria falhar, a operação falha junto (nenhum acesso sem registro). A tabela é só de inclusão: a API não tem grant de UPDATE/DELETE/TRUNCATE e um trigger recusa essas operações até para o dono do schema. Ações e tipos de recurso novos entram em `AUDIT_ACTIONS`/`AUDIT_RESOURCE_TYPES` no model (são enums do Postgres: gere a migração). Hoje são auditados signin, signout, redefinição de senha e todas as rotas de paciente, de consentimento e de registro; todo acesso a paciente, registro ou arquivo deve ser auditado. Listagens gravam um registro por paciente exibido (`auditLogService.recordMany`, com o mesmo `requestId`), para que o relatório de acessos por paciente enxergue quem viu os dados dele numa lista; lista vazia grava um único registro sem `patientId`. Chame a auditoria dentro do mesmo `withOwnerScope`/`withTransaction` da operação: assim uma falha na auditoria desfaz a escrita (`tests/integration/transactions.spec.ts`).
- O hash de senha (bcrypt) é feito no `user.repository` (`save` e `updatePassword`), que também guarda o e-mail em minúsculas; a comparação é feita com `comparePassword(password, user.passwordHash)`.
- Os tokens de e-mail e de senha expirados não são apagados automaticamente (não há TTL no Postgres e a API não tem DELETE); expiram pela checagem de `expiresAt`.
- Logging: use o `AppLogger` (`src/shared/appLogger.ts`, pino) em vez de `console`, com a mensagem fixa e os dados no segundo argumento (`AppLogger.info("User created", { userId })`). O `requestLoggerMiddleware` registra cada requisição e o `requestId` entra automaticamente em todos os logs feitos durante ela; nos testes, o mock do `AppLogger` precisa ter `debug`, `info`, `warn` e `error`. Não registre dados pessoais (nome, e-mail e, futuramente, dados de pacientes) nos logs — identifique registros pelo ID (`{userId=...}`), já que a API vai tratar dados de saúde (dado sensível na LGPD). Para logar um erro, use `AppLogger.error("mensagem", errorDetails(err))` (`src/shared/errorDetails.ts`) e nunca `${err}` ou `err.stack`: o `DrizzleQueryError` traz os parâmetros da consulta (e-mail, nome, CPF) na mensagem e no stack, e o `detail` do Postgres repete os valores duplicados.

## Pontos de atenção

O plano do produto, as decisões já tomadas (dono do paciente, papéis na LGPD, encarregado) e as regras legais que orientam o projeto estão em `docs/roadmap.md`. Siga os princípios de arquitetura de lá (isolamento por enfermeira, histórico com edição versionada e anulação em vez de exclusão, auditoria de acesso, arquivos fora do banco) e marque os checkboxes ao concluir itens.

- Os templates HTML de e-mail ficam em `templates/` na raiz e são lidos em tempo de execução via `process.cwd()`, fora do build do `tsc`. Um template novo nessa pasta já entra na imagem (o Dockerfile copia `templates/` no estágio de produção); se mudar o local, ajuste o `COPY` do Dockerfile.
